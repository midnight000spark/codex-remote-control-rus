# Android 后台连接策略

本文说明 Android APK 切到后台后的 WebSocket 行为、可靠性边界，以及为何当前不引入前台服务（Foreground Service）。

## 当前行为

APK 的 WebSocket 由 `MainActivity` 持有。

- `onStop()` 只将 `activityInForeground` 设为 `false`，不会主动关闭 `BridgeClient`。
- `onDestroy()` 会关闭 WebSocket，取消自动重连，并停止会话同步循环。
- 如果连接意外关闭且已开启“自动重连”，APK 会按退避策略尝试重连；当 Activity 回到前台时，也会尝试恢复连接。
- 桥接端和 Codex 端的任务不依赖 APK 连接而运行。重新连接后，APK 通过权威的 `session.content` / `session.sync` 快照补齐会话状态。

因此，切换到后台本身不会让 APK 主动断线，但它也不表示连接会被系统可靠地保留。

## 可靠性边界

没有前台服务时，后台进程和网络访问受 Android 系统调度与省电影响。锁屏、Doze、省电限制、网络切换和内存压力，都可能导致 WebSocket 心跳延迟、连接中断或进程被回收。

| 场景 | 当前实现的预期 |
| --- | --- |
| 短暂切到其他 App | 通常仍保持连接，但不保证。 |
| 锁屏或长时间后台 | 可能断线，或无法及时处理心跳和重连。 |
| 系统回收进程 | 连接断开；下次打开 App 后恢复。 |
| Wi-Fi、VPN 或移动网络切换 | 连接可能断开；自动重连会在有机会执行时尝试恢复。 |
| Codex 在 APK 离线期间完成任务 | 任务继续在桥接端执行；回到 App 后通过快照看到结果。 |
| APK 离线期间出现审批 | 用户不能实时看到或处理审批，任务可能等待审批。 |

普通通知只用于提示消息、任务完成或错误；它不保活进程，也不能替代前台服务。

## 前台服务会带来什么

将连接移入前台服务后，服务通过持续通知告诉用户连接正在运行，系统会以更高优先级保留它。这样能够显著提升锁屏和后台时 WebSocket 的存活率，并允许后台持续接收进度、任务完成与审批事件。

这并非“永不断线”：断网、网络切换、桥接端重启仍会中断连接。因此，心跳、指数退避重连和会话快照恢复仍然是必需的。

| 方面 | 当前方案 | 前台服务方案 |
| --- | --- | --- |
| 后台实时事件 | 尽力而为 | 更稳定地接收 |
| 审批响应时效 | 可能等到用户回到 App | 可及时通知用户处理 |
| 常驻通知 | 无 | 必须有 |
| 电量与网络消耗 | 较低 | 较高，连接与心跳会持续运行 |
| 实现复杂度 | 较低 | 服务、状态绑定、通知操作和生命周期需要额外维护 |
| 系统/商店合规 | 无前台服务要求 | 需声明合适的服务类型、权限和用户可见通知，并遵守 Android 的前台服务限制 |

若未来实现，连接、心跳和重连应由专用 `BridgeConnectionService` 管理；Activity 仅观察服务状态和展示 UI，不再直接拥有 `BridgeClient`。

## 当前决策

当前项目保持 Activity 持有连接的轻量方案，不引入前台服务。

理由是：远程执行的权威状态在桥接端，APK 断线不会取消 Codex 任务；重新连接后能够用快照恢复。对于“打开 App 发起任务，偶尔切后台，完成后再查看”的主要使用方式，前台服务带来的常驻通知、额外耗电和架构复杂度大于收益。

## 重新评估条件

出现以下需求时，应重新评估引入前台服务：

- 用户经常锁屏或长时间切到后台，仍要求实时查看输出；
- 审批必须在后台及时通知并尽快处理，不能长时间阻塞任务；
- 产品定位改为始终在线的远程终端，而不只是按需查看与控制；
- 可接受常驻“已连接”通知与额外电量消耗。

在实现前台服务前，应先确认目标 Android 版本下适用的前台服务类型、权限和平台政策；不要以静默后台重连替代用户可见的前台服务。
